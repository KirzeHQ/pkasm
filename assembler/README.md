# PkASM Assembler

The assembler is intended to be a target-driven framework, not a collection of architecture-specific Rust implementations.
Its job is to provide one common pipeline for parsing PkASM source, selecting a target, validating instructions, and producing the target's machine code.

## Design Goals

- Make adding an architecture or architecture version primarily a data task.
- Keep the assembler core independent of individual instruction sets.
- Make target selection deterministic and explicit.
- Keep target definitions reviewable, testable, and easy to update.
- Allow the same PkASM source to be compiled for every supported target where the source uses the common language and target capabilities permit it.

## Target Layout

Target definitions live under `src/targets/`:

```text
assembler/
└── src/
    ├── lib.rs
    └── targets/
        ├── latest/
        │   ├── x86.info
        │   └── ...
        ├── <version>/
        │   ├── x86.conf
        │   └── ...
        └── ...
```

The canonical path for a versioned target is:

```text
src/targets/<version>/<arch>.conf
```

`<arch>` is the architecture identifier used by the CLI and project
configuration. `<version>` identifies a concrete version of that architecture,
such as an ISA revision, not necessarily a software release.

The `latest` directory is an index, not another target implementation. Each
`src/targets/latest/<arch>.info` file points to the current versioned target
definition for that architecture. For example:

```text
src/targets/latest/x86.info  ->  ../v1/x86.conf
```

The exact representation of the pointer is an implementation detail to be finalized,
but it must resolve to one concrete `<version>/<arch>.conf` file and must not duplicate the target definition.
These index files should be produced or updated by the assembler's target tooling, not hand-maintained as a second architecture definition.

## Adding an Architecture

The normal workflow should require editing only the new versioned `.conf` file;
the index is generated by the framework and no assembler Rust code changes are needed:

1. Create `src/targets/<version>/<arch>.conf`.
2. Describe the architecture, instruction set, registers, encoding rules, addressing modes, constraints, and other target metadata in that file.
3. Mark the version as the preferred version in the target metadata when it should become `latest`.
4. Let the target tooling generate or update `src/targets/latest/<arch>.info`.
5. Run the assembler's target validation and test suite.

For example, adding an x86 target should look conceptually like this:

```text
src/targets/v1/x86.conf
src/targets/latest/x86.info  # generated target index
```

The `.conf` file is the source of truth for the target.
It should be possible for a contributor to add a large instruction definition without
editing a Rust match statement, registering a new module, or changing the target-selection logic.

## Configuration Responsibilities

The target configuration format will need to describe at least:

- Target and version identity.
- Word size, endianness, alignment, and address size.
- Register names, aliases, widths, and special-purpose registers.
- Instruction names, aliases, operands, and operand constraints.
- Immediate and memory operand rules.
- Instruction encoding and byte layout.
- Relocations, labels, symbols, and unresolved references.
- Sections, directives, alignment, and data emission rules.
- Target capabilities and features that common PkASM code may query.
- Diagnostics for unsupported or invalid operations.

The format should favor declarative data over embedded logic.
Validation should reject incomplete or ambiguous definitions before assembly begins, with errors that identify the target file and relevant field.

## Resolution Model

Target resolution should follow one path for every architecture:

1. Read the requested architecture and optional version from the project or CLI.
2. If no version is supplied, resolve `<arch>.info` in `targets/latest/`.
3. Load the resulting versioned `.conf` file.
4. Parse and validate the definition.
5. Assemble through the generic pipeline using the loaded target model.

A requested version must resolve directly to a concrete target definition.
The assembler should not silently fall back to `latest` when a requested version is missing.

## The Generic Pipeline

Target files should feed a shared pipeline rather than architecture-specific code paths:

```text
source
  -> lexer and parser
  -> target-independent representation
  -> target validation
  -> instruction selection and operand checks
  -> target-defined encoding
  -> relocations and final output
```

The parser should understand PkASM syntax and the assembler should own common concepts such as labels, expressions, sections, diagnostics, and relocations.
The target definition should supply the facts needed to validate and encode architecture instructions.

## Rust Exceptions

Rust is the exception for behavior that cannot reasonably be represented as configuration.
Examples may include the parser, expression evaluator, relocation engine, output writers, and a small extension mechanism for unusual encoding rules.

Such extensions should be generic and capability-based rather than one-off architecture modules.
Adding a normal architecture must not require new Rust code.
If a target genuinely needs custom behavior, that boundary should be explicit, documented in its `.conf`, and covered by focused tests.

## `pkasm.conf`

The assembler will eventually have its own `pkasm.conf` under `src/targets/`. This file is reserved for assembler-language-level definitions shared across targets, such as common syntax, directives, pseudo-instructions, and mappings from the portable PkASM language to target operations.

It must not become a second place for architecture-specific instruction data.
Architecture facts belong in the relevant versioned `.conf` file.

## Portability Boundary

PkASM is intended to provide minimal abstraction:
source should remain close to assembly while still being portable when it only uses the common target surface.
Target-specific instructions and features should remain available,
but the assembler must report their portability requirements clearly rather than pretending they work everywhere.

The assembler should therefore distinguish between:

- Portable language constructs supported by multiple targets.
- Target-defined instructions and operands.
- Explicitly target-specific extensions.
- Constructs that require a capability unavailable on the selected target.
